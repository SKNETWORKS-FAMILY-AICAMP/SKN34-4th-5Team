# 일반 회원·마이페이지 인계서

## 구현 범위와 연결 위치

- `/mypage`: 프로필, 내 코스, 좋아요한 코스, 닉네임·응원팀 수정.
- 헤더: 로그인 → 로그아웃, 회원가입 → 마이페이지.
- `/login`의 아이디·비밀번호 입력으로 개발용 일반 회원에 재진입 가능.
- `frontend/lib/member-preview.ts`: 미리보기 상태와 프로필 저장 어댑터.
- `frontend/components/member-header-actions.tsx`: 헤더 상태 표시.
- `frontend/app/mypage/page.tsx`: 화면. 코스 조회는 기존 `useRoutes`, 좋아요는 `useLikedRoutes` 사용.
- 코스 수정·상세는 기존 `/routes/new?edit={id}`, `/routes/{id}` 이용. 삭제는 기존 상세에서 수행.
- 게시글·댓글 관리, 비밀번호 변경, 회원 탈퇴, 실제 인증은 이번 마이페이지 작업 범위 밖.

## 임시 데이터의 경계

`NODE_ENV=development`이면서 `NEXT_PUBLIC_MEMBER_PREVIEW=true`일 때만 가상 회원 사용. 배포 빌드에서는 비활성화된다. 기본 가상 회원은 `id=preview-member`, `nickname=직관팬`, `role=member`, `mode=preview`다. 최초 접속은 로그아웃 상태이며 로그인 성공 후 로그인 여부를 저장한다. 기존 브라우저의 로그인 상태는 유지한다.

`kbo-member-preview-v1` localStorage에 signedIn/nickname/teamCode/avatar를 보관한다. 비밀번호·JWT·관리자 권한은 넣지 않는다. 이 상태는 실제 `/admin-api`·팀 챗봇 인증에 전달하거나 사용하지 않는다. 팀 로그인 쿠키와 미리보기 로그인은 별개이며 미리보기 로그아웃은 팀 JWT를 변경하지 않는다.

내 코스는 현재 브라우저 저장 코스 중 isSample=false인 항목이다. 실제 회원 소유권을 검증한 목록이 아니며, 기존 브라우저 코스를 자동으로 팀 계정 소유로 옮기지 않는다. 좋아요 역시 기존 브라우저 저장 목록이다. 로그아웃해도 기존 데이터는 삭제하지 않는다. 사용자 전환이 가능한 다중 계정 모드는 제공하지 않는다.

## 제안 API 계약 (백엔드 합의 전)

기존 팀 `/auth/user`와 중복 회원 API를 만들지 말고 프로필 조회는 확장하거나 어댑터로 통합한다. 다음 경로는 제안이며 현재 팀 서버에 구현된 것으로 간주하지 않는다.

| API | 요청 | 응답/역할 |
| --- | --- | --- |
| GET /api/me | 인증 쿠키/JWT | id, username, nickname, favoriteTeamCode, role |
| PATCH /api/me | nickname(1~20자), favoriteTeamCode | 검증 후 갱신된 프로필 |
| GET /api/me/courses?page=1&pageSize=20 | 인증 | count, results: 코스 목록 |
| GET /api/me/liked-courses?page=1&pageSize=20 | 인증 | count, results: 좋아요한 코스 목록 |
| POST /api/courses | title, stadiumCode, stops, start, content, contentFormat 등 | 서버 발급 id, 6자리 routeNumber, createdAt |
| PATCH /api/courses/{id} | 변경할 코스 내용 | 갱신 코스 |
| DELETE /api/courses/{id} | 없음 | 204 |
| PUT /api/courses/{id}/like | 없음 | 좋아요 등록, 멱등 |
| DELETE /api/courses/{id}/like | 없음 | 좋아요 취소, 멱등 |

인증 실패 401, 권한 없음 403, 필드 검증 오류 400, 없는 코스 404. 실제 연동에서는 조회 로딩·오류·재시도·페이지네이션을 추가하고 가상 상태 대신 인증 응답을 사용한다.

## DB 모델 제안

- 사용자: 기존 CustomUser 재사용. nickname 및 favorite_team_code 추가 여부 합의. 닉네임 중복 정책은 백엔드 결정 필요.
- 코스: owner FK(CustomUser), title, stadium, content, content_format, created_at, updated_at, route_number(unique). 코스 번호는 `ROUTE_NUMBER_HANDOFF.md` 준수.
- 방문 지점: course FK, sequence, place_provider/place_id, name, lat/lng, category, address. 같은 장소 재방문 허용: place_id를 코스 내부 unique로 두지 않고 (course, sequence)로 순서 보장. 출발 좌표는 별도 보존.
- 좋아요: user FK, course FK, created_at, unique(user, course).
- 필드·테이블 생성과 변경은 Django 모델과 migration으로 수행. 이번 작업은 DB 변경을 하지 않음.

## 보안·이관 규칙

- 실제 소유자는 인증된 request.user로 결정하며 클라이언트 owner_id/role/is_staff를 신뢰하지 않는다.
- 조회·수정·삭제 모두 서버에서 본인 소유권 확인. 공개 코스 조회와 내 코스 관리 권한을 분리.
- 브라우저 코스 가져오기는 로그인 후 사용자 선택과 서버 검증을 거쳐 진행. local ID를 서버 ID로 매핑하며 재요청 시 중복 저장 방지 필요.
- 서버 로그인 성공 시 브라우저별 가상 데이터와 섞이지 않게 미리보기 어댑터를 제거/비활성화.

## 인수 체크리스트

- 로그인 후 헤더 전환, 로그아웃 후 마이페이지 접근 차단.
- 프로필 저장·재조회, 유효하지 않은 팀 코드/빈 닉네임 거부.
- 사용자 A/B의 내 코스·좋아요 격리, 다른 사용자 코스 변경 403/404.
- 코스 저장·수정 후 내 코스 갱신, 출발·도착 동일 장소와 반복 방문 순서 보존.
- 좋아요 중복 요청·취소, 삭제된 코스 처리, 네트워크 실패·인증 만료 처리.
- 프로덕션에서 개발용 미리보기 경로가 실제 인증을 우회하지 않는지 확인.

## 개발용 계정 로그인 (추가)

- 서버 전용 `.env.local`의 `MEMBER_PREVIEW_USERNAME`, `MEMBER_PREVIEW_PASSWORD`로 고정 테스트 계정 설정. 실제 비밀번호는 Git·문서·클라이언트 번들에 넣지 않는다.
- `/team-auth/login`은 개발 모드 + 미리보기 활성화 + 설정된 아이디 일치 시 서버에서 비밀번호를 비교한다. 불일치하면 401, 성공하면 `{ok:true, mode:"preview"}`를 반환한다.
- 로그인 화면은 성공 응답 후 기존 가상 회원 상태를 켜고 `/mypage`로 이동한다. 암호 없이 진입하는 미리보기 버튼은 제거했다.
- 다른 아이디는 기존 팀 로그인 경로를 사용한다. 개발용 로그인은 JWT를 발급하지 않으며 관리자·팀 API 권한을 제공하지 않는다. localStorage 상태는 UI 테스트용이며 실제 인증 수단이 아니다.
- 로그아웃 후 같은 계정으로 재로그인해도 이 브라우저의 프로필·코스는 유지된다. 다른 브라우저로 데이터가 동기화되지는 않는다.

## 프로필 사진 업로드 (2026-09-13)

### 참고와 우리 기준
- [Reddit 공식 도움말](https://support.reddithelp.com/hc/en-us/articles/360043036152-How-do-I-update-my-avatar-image): 프로필 설정에서 컴퓨터 이미지 선택. 해당 안내에는 용량 제한이 명시되어 있지 않음.
- [Discord 공식 도움말](https://support.discord.com/hc/en-us/articles/4403147417623-Custom-Profiles): 아바타 변경 → 적용 → 저장. 애니메이션 GIF는 Nitro 기능. 배너의 10MB 제한을 아바타 제한으로 혼동하지 않음.
- [GitHub 공식 기준](https://docs.github.com/en/account-and-profile/reference/profile-reference): PNG/JPG/GIF, 1MB 미만, 3000×3000 미만, 약 500×500 권장.
- 우리 서비스 선택: JPG/PNG/WebP, 5MiB 이하. 최소 각 변 64px, 최대 각 변 10,000px 및 4천만 화소 이하. 중앙 정사각형 크롭 → 512×512 JPEG(품질 0.85), 원형 표시. GIF/SVG는 입력 불가. 투명 배경은 흰색 처리. 이 수치는 타 서비스의 공통 규칙이 아닌 우리 프로젝트 기준.

### 현재 구현
- 마이페이지 → 회원정보 → 사진 선택 → 원형 미리보기 → 사진 저장. 취소하면 기존 사진 유지. 기본 이미지로 선택 후 사진 저장하면 삭제.
- `frontend/components/profile-photo-editor.tsx`: 파일 선택, 미리보기, 저장/취소 UI.
- `frontend/lib/profile-image.ts`: 형식·용량·디코딩·해상도 검사, 크롭과 재인코딩. 원본 파일명/EXIF는 저장하지 않음.
- `frontend/lib/member-preview.ts`: avatar 데이터 URL 저장. 닉네임 수정·로그아웃 시 사진 유지. 구버전 데이터에는 빈 avatar 기본값.
- 현재는 서버 업로드가 아닌 브라우저 보관이며 저장 공간 부족 오류 표시. 원본 사진은 서버로 보내지 않음. 실제 인증/DB와 분리.

### 백엔드 연결 제안
- `PUT /api/me/avatar`: multipart `file` → `{avatarUrl}`. `DELETE /api/me/avatar`: 기본 이미지로 복원. 기존 프로필 응답에 avatarUrl 추가. 경로는 합의 전 제안.
- 서버 인증 사용자로 소유권 결정. 파일 확장자/클라이언트 MIME만 믿지 말고 실제 바이트와 이미지 디코더로 형식 검사. 파일 용량 제한과 디코딩 전 픽셀 제한 적용, 서버에서도 512×512 재인코딩 및 메타데이터 제거.
- 사용자 모델에 이미지 URL/스토리지 키만 두고 파일은 미디어 저장소에 저장. 파일명은 서버 생성. 교체 성공 후 이전 파일 정리. DB 변경은 Django 모델/migration으로 담당자가 수행.
- 실패: 비로그인 401, 형식 415, 용량 413, 손상/해상도 400. 기존 사진 유지. 실제 운영 시 이미지 신고/운영 기준도 팀에서 결정.
- 확인 항목: 정상 선택/저장/재접속/삭제, 취소, 같은 파일 재선택, 잘못된 형식, 손상 이미지, 5MiB 초과, 저장소 용량 부족. 프론트 검증은 서버 보안 검증의 대체가 아님.

## 회원 등급 / 닉네임 변경 제한
- 기존 1·2·3단계 이미지 시안은 폐기된 이전 기획이다. 현재 등급제는 1~5등급이며, 등급 아이콘·표시 방식은 현재 회원 등급 UI 구현을 따른다.
- 현재 가상 계정은 항상 1단계. 닉네임 오른쪽 30px 뱃지 표시. 실제 회원 등급은 누적 등급 포인트(`PointWallet.total_earned`)로 서버에서 산정하며, 1등급 0~99점, 2등급 100~249점, 3등급 250~499점, 4등급 500~749점, 5등급 750점 이상이다.
- 닉네임 실제 변경 성공 시 nicknameChangedAt 기록. 이전 값과 같은 닉네임 저장·응원팀/사진 변경은 제한을 시작하거나 연장하지 않음. 이전 기록이 없는 현재 계정은 첫 변경 가능.
- 한국 시간 기준 달력상 6개월 후 같은 시각부터 재변경 가능. 해당 월에 날짜가 없으면 말일로 보정. 예: 8월 31일 → 다음 해 2월 28/29일. UI에 다음 변경 가능 시각 표시.
- 현재 localStorage 기반 제한은 개발용. 서버 연동 시 nickname_changed_at과 nickname_change_available_at을 프로필 응답에 포함하고, 서버 시각·트랜잭션으로 변경과 제한을 원자적으로 검증. 프론트 날짜나 클라이언트 등급을 신뢰하면 안 됨.
- 가입 보상 100포인트는 잔액(`balance`)에만 반영하고 누적 등급 포인트에는 반영하지 않는다. 따라서 가입 직후 신규 회원은 1등급이며, 활동 보상과 환상야구 정산 등 등급 대상 적립만 `total_earned`에 반영한다.
- 포인트 사용·환불·관리자 조정은 별도 등급 반영량(`rank_delta`)이 없으면 등급 산정에 반영하지 않는다. 지급과 등급 포인트 갱신은 하나의 트랜잭션으로 처리하며 중복 지급과 음수 잔액·누적값을 허용하지 않는다.
- 포인트 지갑이 없는 회원과 등급 정보가 없는 기존 응답은 기본 1등급으로 취급한다. 기존 코스처럼 `owner`가 비어 있는 데이터는 등급을 표시하지 않는다.

## 추가 계정 설정·알림 (2026-09-13)
- 닉네임: 한글 완성형/영문 A-Z a-z만 1~12자. 숫자·내부 공백·특수문자 제외. 기존 6개월 제한 유지. 변경은 UI와 저장 어댑터에서 검사. 기존 데이터는 임의로 잘라 수정하지 않음.
- 이메일: 입력 형식 검사 후 개발용 저장. 이메일 미인증 상태이며 실제 복구 수단으로 사용하지 않음. 서버에서는 새 이메일 인증 완료 후 반영하며 기존 주소에 변경 통지 필요.
- 알림 수신 설정: 댓글·답글, 코스 반응, 공지·회원 소식. 알림함은 로그인한 회원의 마이페이지 버튼 오른쪽 종으로 열림. 읽지 않은 알림 수만 우측 하단 빨간 원/흰 글씨, 0은 숨김, 100 이상 99+. 개별/모두 읽음, 빈 상태, Escape/바깥 클릭 닫기 구현.
- 실제 댓글/코스 알림 서버 연결은 미구현. addMemberNotice(kind,text) 어댑터 제공. 가짜 알림은 생성하지 않음. 개발용 비밀번호 변경 성공 시 공지·회원 소식 수신이 켜져 있으면 실제 변경 알림 생성.
- 활동 공개: 내 코스, 내 글·댓글 활동 목록, 좋아요한 코스 각각 선택, 기본 비공개. 공개 프로필 서버 미구현으로 현재 설정 저장만 수행. 공개 게시글 자체의 공개 여부와 활동 목록 노출은 다름.
- settings 저장소: kbo-member-settings-v1, email/notifications/visibility/notices. 최대 100건, 읽음 상태 유지. 현재 단일 가상 회원용이며 실제 연동 시 계정별 격리 필요.
- 비밀번호: POST /member-preview-password (개발 모드 전용), 현재 비밀번호 확인, 새 암호 8~128자 영문·숫자·특수문자 포함 및 공백 제외, 기존과 다른 값. 브라우저에 비밀번호 저장 안 함.
- 변경된 암호는 frontend/.member-preview/credentials.json에 scrypt salt/hash로 저장하고 Git 제외. 기존 env 암호보다 우선하며 개발 서버 재시작 후 유지. 변경 기록이 없으면 env 암호 사용. 팀 JWT/DB에 적용되지 않음. 실제 계정은 팀 인증 서버의 암호 변경/재인증/세션 무효화로 교체해야 함.
- 제안 API: PATCH /api/me/settings, 이메일 변경 요청·확인 API, POST /api/me/password, GET /api/me/notifications (미읽음 총수 포함), PATCH 알림 읽음. 서버에서 request.user 기준 조회/수정·공개범위 강제·알림 수신 설정 적용. 이메일/권한/보안 알림 정책은 팀 합의 필요.
- 검증: 타입/ESLint 통과. 임시 디렉터리에서 암호 변경 전후 검증, 기존 암호 거부, 해시 저장 확인. 실제 사용자 비밀번호는 테스트로 변경하지 않음.

### 이메일 인증 팝업 및 설정 배치 수정
- 이메일 입력은 변경 팝업으로 이동. 인증 메일 받기 버튼은 서버 연결 전임을 안내하며 메일 발송/인증 성공을 가장하지 않는다. 인증 전 기존 이메일 보존. 이메일 직접 변경 저장은 제거.
- 활동 공개 범위를 알림 설정보다 먼저 표시. public-likes 라벨은 좋아요, 추천 목록 공개로 확대. 서버 연결 시 코스 좋아요 외 게시글 추천 목록도 같은 공개 설정 적용 필요.
- 닉네임 입력 너비 50%. 화면의 이메일/공개 범위 설명은 제거하고 실제 제약은 인계서에 유지.

## 포인트 등급 기준 확정 (이전 미정 기준 대체)
- 0~500pt: 1단계, 501~1000pt: 2단계, 1001pt 이상: 3단계. level은 points로 계산, 별도로 불일치하게 저장하지 않음.
- 현재 개발용 회원은 기존 points 필드가 없으면 56pt로 시작. 실제 획득 이력이 아닌 사용자 지정 미리보기 값. 뱃지 오른쪽 하단 정렬, 11px 표시.
- 획득 경로: 출석체크, 내 루트가 받은 추천, 승부 예측. 경로별 지급량·횟수·예측 보상 조건은 미정. 자동 적립은 아직 구현하지 않음.
- 실제 서버에서는 포인트 원장과 이벤트 고유키로 중복 지급 방지, 서버 계산 잔액을 응답. 추천 취소/본인 추천/예측 정산/출석 일자 기준은 추후 합의. 프론트 points는 권한·보상 근거로 사용하지 않음.

### 이메일 코드 확인 단계
- 팝업: 새 주소 → 인증 코드 받기 → 메일로 받은 6자리 숫자 입력 → 인증하고 이메일 변경. 발송 성공 전 입력/확인 비활성화. 주소 변경·재발송 시 기존 requestId와 입력 코드 초기화.
- /member-email-verification POST 계약: send {email} → {requestId}, verify {email,requestId,code} → {verified:true,email}. 검증 성공 응답에만 이메일 갱신.
- 현재 엔드포인트는 메일 서비스 미연결로 503 반환. 실제 발송·코드 검증은 미구현이며 임의 인증 성공 처리 없음.
- 백엔드 필수: 로그인/재인증, 요청을 사용자와 새 이메일에 결속, 코드 만료·실패 횟수 제한·재발송 제한·일회성 사용, 서버에서 실제 이메일 변경. 코드를 응답/로그에 노출하지 않음.

## 받은 메시지함
- 헤더 순서: 마이페이지 → 편지 아이콘 → 알림 종. 로그인 상태에서만 표시. 편지 버튼으로 받은 메시지 목록/본문 조회, 열람 시 읽음 처리, 안 읽은 메시지 수 뱃지 제공.
- 현재 kbo-member-inbox-v1 개발용 어댑터, 초기 빈 목록. 실제 메시지 송수신 서버 미연결이며 임의 메시지 생성 없음. 메시지 발송 기능은 이번 범위 밖.
- 계약 제안: GET /api/me/messages (페이지네이션 및 unreadCount), GET 상세, PATCH 읽음. 서버는 수신자 소유권 확인 필수. 필드 id/sender/subject/body/createdAt/read. 실제 연동 시 브라우저 가상 저장 대신 서버 응답 사용.

### 다른 회원 코스를 바탕으로 코스 만들기
- 코스 상세의 추천 안내 상자는 현재 다른 회원 역할의 샘플 코스에서만 표시하며, 내 로컬 코스에서는 숨깁니다. 실제 연동 시 isSample 대신 로그인 회원 ID와 코스 owner ID를 비교해야 합니다.
- 코스 수정하기 버튼은 이동 확인 후 /routes/new?copy=원본ID 로 연결합니다. 방문 지점, 출발지와 작성 정보를 초기값으로 불러오고 저장 시 새 ID의 내 코스를 생성합니다. 원본의 추천수·조회수·작성자는 승계하지 않습니다.
- 복사 초안은 기존 수정 초안과 분리합니다. 백엔드 연동 시 공개/열람 권한 검사와 새 코스 생성 API로 처리해야 합니다.

### 팀 게시글 추천·비추천
- 상세 제목은 팀 shortName + 기존 색상 말머리 + 제목 순서입니다. 본문 최소 높이는 PC 390px, 모바일 330px입니다.
- 본문 아래 중앙의 추천/비추천은 상호 배타적으로 선택하며 같은 버튼을 다시 누르면 취소됩니다. 현재 브라우저 localStorage(kbo-community-votes-v1)에만 저장하고 목록·상세 추천수를 함께 반영합니다.
- 백엔드 연결 시 회원 ID와 게시글 ID의 유일 제약, 원자적 투표 변경/취소, 서버 집계 추천·비추천수를 제공해야 합니다. 현재 비추천의 기본 집계는 0이며 실제 회원 투표/포인트 지급과 연결되지 않았습니다.

### 게시글 하단 프로필·댓글·탐색 UI
- 작성자 기본 이미지/이름/팀 프로필 카드, 댓글 0개 빈 상태와 입력란, 등록순·최신순·새로고침을 표시합니다. 현재 댓글 작성과 글쓰기 버튼은 서버 미연결 안내를 표시하며 접수/저장 성공을 가장하지 않습니다.
- 목록, 현재 필터의 다음글/이전글(경계 비활성), 이전페이지, 맨위로를 제공합니다.
- 인벤 참고 페이지: https://www.inven.co.kr/board/lostark/6271/4096027 . 외형은 기존 커뮤니티 스타일 유지.
- 백엔드 연결 시 작성자 공개 프로필, 댓글 조회/정렬/생성 API와 권한 검사, 상세·목록 댓글 집계 동기화가 필요합니다.

### 내가 쓴 글
- /mypage?tab=posts 및 헤더의 찜한 코스 아래 메뉴를 추가했습니다. 태그는 전체/자유게시판/팀 게시판/승부 예측/코스 후기입니다.
- 현재 커뮤니티는 예시 데이터뿐이므로 내 글로 포함하지 않습니다. 저장된 비샘플 코스 중 실제 본문이 있는 항목만 코스 후기로 표시합니다.
- 백엔드는 인증 회원을 기준으로 영역별 작성 글을 집계하는 GET /me/posts?area=all API와 id/area/title/detailUrl/createdAt/authorId 필드를 제공해야 합니다. 클라이언트 닉네임 비교 대신 서버에서 소유권을 확인해야 합니다. 실제 게시글/후기 공개 상태를 구분해 저장만 한 코스는 제외합니다.

### 내가 쓴 글과 내 코스 분리 (최신 수정)
- 앞서 작성한 '저장 코스의 본문을 내가 쓴 글에 표시' 방식은 폐기합니다. MemberPosts는 저장 코스 목록을 받지 않고 별도의 authored-post 데이터를 받습니다.
- 전체/자유게시판/팀 게시판/승부 예측/코스 후기 태그를 유지합니다. 코스 후기도 실제 게시글로 등록된 항목만 포함하며 단순 저장 코스나 본문 유무로 추정하지 않습니다.
- 현재 작성 글 API가 없어 빈 목록입니다. 추후 /me/posts 결과를 연결하고 코스 저장 API와 독립 관리합니다.

- 코스 후기의 최종 버튼은 '작성 완료'. 완료 시 저장 후 /routes(코스 둘러보기)로 이동하며 useRoutes 목록에 표시한다. 현재 브라우저 로컬 저장 기반이므로 다른 회원에게 실제 공개하려면 백엔드 게시 API 연동이 필요하다.
