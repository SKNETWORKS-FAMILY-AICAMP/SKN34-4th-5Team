# Docker 재시작 후 숙박 수정 실패 복구

검증일: 2026-10-13. 로컬 `feat/course-planner-stability`, 기반 커밋 `8cb4eb5`.

## 증상과 원인

잠실 2026-10-16 17:00 가상 경기 코스에서 “난 카페 무조건 메가커피 가야해. 메가커피로 바꿔줘 그리고 산책 말고 숙박으로 일정 수정해줘” 요청이 두 번 실패했다. 저장된 사용량 원장 기준 전체 채팅 처리 시간은 각각 약 10.88초와 6.35초였다.

- 별도 재현에서 메가MGC커피 삼성다형점 선택은 성공했다.
- 숙박 후보는 15곳 있었고, 실제 조사한 12곳은 모두 `unavailable`, `stage=startup`이었다. 조건 불일치나 실제 숙소 부재를 확인한 결과가 아니다.
- Docker 재시작 후 컨테이너 쓰기 계층에 이전 `/tmp/.X99-lock`, `/tmp/.X11-unix/X99`, `/tmp/squid.pid`가 남았다.
- Xvfb는 `Server is already active for display 99`, Squid는 기존 PID 파일 때문에 종료했다. 프로세스 목록에서도 둘 다 종료된 상태였다.
- MCP API 프로세스는 살아 있어 컨테이너가 실행 중으로 표시됐다. 프런트엔드와 Django HTTP 200 확인만으로 숙박 브라우저의 준비 상태를 확인할 수 없었다.
- 숙박 확인 실패로 복합 수정 전체를 취소하는 기존 처리에 따라 메가커피 교체도 적용되지 않았다.

## 변경

`docker-compose.yml`의 `jev-browser`에 512MiB `/tmp` tmpfs를 지정했다. 컨테이너가 다시 시작될 때 브라우저 임시 파일이 초기화되며 DB·Qdrant·업무 데이터 볼륨은 변경하지 않는다.

MCP API 포트, Squid 프록시 포트, Xvfb Unix 소켓 연결을 확인하는 healthcheck를 추가하고 숙박 워커는 브라우저의 `service_healthy`를 기다리도록 했다. 네트워크 차단 규칙, Chrome sandbox, 출처·주소 검증, 모델 호출 경로는 변경하지 않았다. 이 상태 확인은 실제 외부 사이트 수집 성공을 보장하지 않으므로 실제 Chrome 조회도 별도로 검증했다.

## 실제 검증

1. 수정 전 저장된 코스·출발지·요청을 별도 호출해 같은 실패를 재현했다. 엔진 처리 4.50초, 숙박 12곳 모두 시작 단계 실패.
2. 브라우저 컨테이너에 변경 설정을 적용한 후 같은 입력으로 **17.287초**, `course:edit` 성공. 메가MGC커피 삼성다형점과 호텔상주로 교체하고 통밥·경기·안주마을 달보드레키친을 유지했다.
3. 숙박은 호텔봄·폼호텔·칸호텔 검색 결과 없음 이후 호텔상주 원문을 확인했다. 네 후보 모두 페이지 캐시 적중 없이 조사했다. 호텔상주의 NOL 상호는 `잠실 상주 호텔`, 주소는 `서울특별시 송파구 올림픽로8길 19`, 출처는 `https://nol.yanolja.com/stay/domestic/3012557`이었다.
4. 같은 컨테이너를 `compose restart`로 다시 시작해 healthy 복귀를 확인했다. 이후 페이지 캐시 읽기를 비활성화한 별도 호텔상주 조회도 **9.273초**, `status=read`, `cache_hit=false`로 성공했다.
5. `git diff --check` 통과.

17.287초는 코스 에이전트 내부 호출 시간으로 전체 HTTP·SSE 시간과 다르다. 한 번의 복구 표본을 전체 요청의 성공률·지연 보장으로 해석하지 않는다. 기존 사용자 대화와 지도는 진단 실행으로 덮어쓰지 않았다. 원시 진단은 Git 제외 경로 `backend/artifacts/diagnose-lodging-edit-20261013*.json`에 보관한다.
