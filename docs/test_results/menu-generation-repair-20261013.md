# 새 코스 메뉴 실패 수정 · 2026-10-13

## 원인

일반 중국집은 자장면 추천 후보로 인정한다는 사용자 정책을 반영했다. 특정 가게를 캐시에 추가하지 않았다.

1. 실제 실패한 새 코스에서 해석 결과의 식당 표현이 `돈카츠먹고 구장 가고 싶어`였다. 방문 정규화가 이 문장 전체를 식당 조건에 넣었고, 단순 메뉴 문법이 뒤의 구장 이동 표현을 소비하지 못했다. 기존 전문 업종 추천 경로 대신 의미 해석·근거 검사로 흘렀다. 같은 요청도 모델이 `돈카츠먹고`까지만 반환하면 경로가 달라지는 재현 가능한 원인이었다.
2. 단순 경로는 돈카츠를 돈까스로 정규화했지만 의미 해석 결과는 같은 정규화를 하지 않았다. 검색어 확장만으로는 이후 조건 비교의 불일치를 해결하지 못했다.
3. 자장면은 짜장면으로 이미 정규화됐고 중국집 후보도 조회됐다. 그러나 별도 메뉴 근거를 요구하면서 근거 저장소가 비어 있고 신규 웹 검색이 꺼진 환경에서는 모두 탈락했다. 읽을 수 있는 매장 프로필의 메뉴도 조건 확인에 연결하지 못했다. 따라서 모든 문제가 동의어 검색 누락이었던 것은 아니다.

평가 지침서를 매 요청마다 추가 실행해서 생긴 문제가 아니라 실제 조건 전달·정규화·근거 처리 코드의 문제였다.

## 변경

- 메뉴 뒤의 완전한 긍정 구장 이동 표현은 일정 문법으로 처리한다. 부정·주차·다른 음식 등 알 수 없는 뒤 문장을 잘라 버리지 않는다.
- 의미 해석을 거친 메뉴도 기존 `canonical_menu_term`으로 통일한다. 한정된 별도 메뉴를 임의로 일반 메뉴로 바꾸지 않는다.
- balanced 추천에서는 일반 중국요리 업종을 자장면 후보로 인정한다. 단순 새 코스·교체뿐 아니라 의미 해석된 복합 요청에도 적용한다. 양꼬치·마라탕·딤섬 전문 업종과 구장 내부 매장으로 확대하지 않는다. 돈카츠는 실제 돈까스 전문 업종/상호 조건을 유지한다.
- 업종에 따른 추천은 `catalog_recommendation`으로 구분하며 메뉴판을 읽은 근거로 저장하거나 표시하지 않는다. 추가 조건·제외 조건·확인된 비판매 근거를 덮지 않는다. 명시적으로 실제 메뉴 근거를 요청한 strict 경로는 유지한다.
- 메뉴 근거가 필요한 경로에서는 기존 프로필 수집기로 실제 메뉴 본문을 읽는다. 매장명·주소·본문 메뉴 구역·동의어·판매 중단을 확인한다. 이 읽기를 신규 웹 검색 허용 설정에 종속시키지 않으며 별도 메뉴 판독 LLM은 추가하지 않았다. 기존 2개 병렬·조회 시간/후보 수 제한과 취소 처리를 재사용한다.

## 고정 사례 A/B

DeepEval 4.2.8과 Ragas 0.4.3에서 같은 42개 사례의 실제 반환 대상/후보를 정답과 정확히 비교했다. 외부 연결과 평가 캐시는 차단했고 유료 평가 모델은 없다. 정답 매장을 가짜 운영 데이터로 저장하지 않았다.

| 구분 | DeepEval | Ragas |
| --- | ---: | ---: |
| A: 이번 수정 전 메뉴 처리 | 30/42 | 30/42 |
| B: 수정 후 메뉴 처리 | 42/42 | 42/42 |

A는 HEAD `4437abf`에서 진행 중이던 카페 수정은 보존하고 이번 메뉴 변경만 되돌린 모듈을 별도 프로세스에 적재했다. 서버 파일을 롤백하지 않았다. 동일 사례 SHA-256은 `e7babaf0ce571e9709df7ca8189541d166aa3bc548e7d6c15816b3eb2d5da691`이다. 원본 모듈 해시와 사례별 결과는 [JSON 기록](menu-generation-repair-20261013.json)에 있다.

사례는 새 코스의 구장 이동 접미사, 메뉴 동의어, 프로필 메뉴 표기, 메뉴와 소스/판매 중단의 구별, 외부 식당·내부 간식·술집의 교체 대상 보호, 중국집 정책과 복합·부정·strict 조건을 포함한다. 중국집 정책 자체는 이번 사용자 변경 사항이므로 총점 차이를 동일한 기존 품질 기준에서의 모델 정확도 상승으로 주장하지 않는다. 고정 fixture에서의 기능 회귀 결과이며 실제 제공자의 일반적인 성공률을 측정한 결과가 아니다.

## 실제 요청 재현

잠실·출발지 미지정·10월 16일 17시 가상 경기 기준으로 별도의 로컬 채팅 세션을 생성했다. 기본 출발지는 종합운동장역이다. 실제 v2 채팅 완료 이벤트까지의 서버 시간을 기록했으며 브라우저·프록시 시간은 제외한다.

| 단계·요청 | 결과 | 시간 | 분류 / 채팅 모델 / 임베딩 호출 |
| --- | --- | ---: | --- |
| 수정 전 · 돈카츠 | 후보 조회 후 식당 탈락, 코스 없음 | 27.017초 | 1 / 4 / 1 |
| 수정 전 · 자장면 | 중국집 후보 조회 후 모두 탈락 | 31.126초 | 1 / 3 / 1 |
| 구조 수정 · 돈카츠 | 사보텐 신천점 → 잠실 | 12.421초 | 1 / 1 / 1 |
| 구조 수정 · 자장면 | 짬뽕지존 잠실새내점 → 잠실, 메뉴 본문 확인 | 18.157초 | 1 / 1 / 1 |
| 중국집 정책 적용 · 자장면 | 빈궁 → 잠실 | 8.995초 | 1 / 1 / 1 |
| 동적 캐시 분리 · 짜장면 | 빈궁 → 잠실 | 10.642초 | 1 / 1 / 1 |
| 동적 캐시 분리 · 돈카츠 | 사보텐 신천점 → 잠실 | 7.109초 | 1 / 1 / 1 |

마지막 두 건은 해당 시험 프로세스의 Django 캐시를 DummyCache로 분리하고 SQL 조건 근거 읽기·쓰기·재시도 냉각을 우회했으며 판정 캐시는 비어 있는 별도 메모리를 사용했다. 운영 캐시는 삭제하지 않았다. 정적 수집 자료·Qdrant·제공자 프롬프트 캐시까지 제거한 비용 비교는 아니다. 두 건은 경로 조회 일부 실패에 따른 기존 이동시간 추정을 포함한다. 음식점과 경기 일정 생성 성공을 모든 경로 API의 성공으로 표시하지 않는다.

생성된 5건 모두 10월 16일 17시·가상 경기 표시·16:40 구장 도착을 유지했다. 실패한 2건도 표에서 제외하지 않았다. 정책·캐시 조건과 모델 해석 결과가 달라 이 시간을 동일 조건 성능 개선율이나 비용 개선율로 계산하지 않는다.

## 회귀 및 CI 연결

`.github/workflows/evaluation-regression.yml`의 `deterministic`에서 아래 오프라인 회귀 명령과 DeepEval export를 실행한다. `highlight-deterministic`은 export 결과를 Ragas로 채점한다. 이 작업에서는 실제 연결 명령을 분리된 로컬 평가 컨테이너에서 실행했다. GitHub 원격 CI를 실행했다는 뜻은 아니다.

```text
python -I .github/evaluation_ci.py offline-exec backend/llm/v2/tests/run_attachment_offline.py llm.tests.test_course_tonkatsu llm.tests.test_course_catalog_conditions llm.tests.test_course_profile_features llm.tests.test_course_recommendation_policy llm.tests.test_course_literal_edits llm.tests.test_course_audit_repairs.CourseSelectionRepairTest
python -I .github/evaluation_ci.py offline-exec backend/manage.py test llm.tests.test_course_evidence --settings=llm.tests.highlight_settings --noinput --verbosity=2
python -I .github/evaluation_ci.py offline-exec backend/llm/v2/evaluation/tonkatsu_contract.py export --output <export.json>
python -I .github/evaluation_ci.py offline-exec backend/llm/v2/evaluation/tonkatsu_contract.py score --input <export.json> --output <ragas.json>
python -I .github/test_evaluation_ci.py
```

- 실제 CI 명령: SQLite 격리 회귀 65개, 일회용 PostgreSQL 근거 회귀 35개, CI 연결 검사 11개 통과.
- 생성·준비·병렬 조회·부분 수정·방문·동선·근접 후보·취소·숙박·코스 전용 응답·근거 관련 확장 회귀 211개 통과. 위 검사들과 중복되므로 합산해 고유 사례 수로 표시하지 않는다.
- 초기 회귀의 자장면 표기 기대값, 종전 중국집 제외 기대값은 미리 기록한 정규화/사용자 정책에 맞춰 갱신했다. CI 연결 검사도 확장된 실행 목록을 검사하도록 갱신했다.
- 최초 최소 CI 설정에서는 모의 검색 테스트의 출력 토큰 설정 누락이 드러났다. 해당 테스트에 설정을 명시한 후 같은 명령으로 35개 통과했다. 운영 설정이나 품질 기준을 낮춘 수정이 아니다.
- 운영 컨테이너에 평가 의존성을 설치하지 않았다. 별도 평가 환경의 LangChain 버전은 운영 환경과 다를 수 있어 실제 제공자 재현은 운영 컨테이너에서 수행했다.
