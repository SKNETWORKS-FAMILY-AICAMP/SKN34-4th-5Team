# 코스 생성과 수정 평가 데이터

사용자가 실제로 요청한 광주·잠실 코스를 기준으로 핵심 6종과 회귀 14종을 평가할 문항, 기대 조건, 공통 입력을 정리했습니다. **현재 상태는 독립 검토 전 초안이며 실제 코스 실행 결과는 없습니다.** 기존 실측 자료는 수정 전 공통 입력을 만드는 데만 사용했습니다.

## 파일

| 파일 | 내용 |
| --- | --- |
| [cases.json](cases.json) | 20개 문항, 출발 좌표·경기·원본 코스 연결, 방문별 기대 조건, 채점 기준 |
| [fixtures.json](fixtures.json) | 광주·잠실 원본 코스 2개와 선택 카페 입력 1개, 출처·변환 내역·해시 |
| [results.template.json](results.template.json) | 문항별 미실행 기록 양식. 시간·비용·호출 수는 null |
| [무결성 검사](../test_course_dataset.py) | 네트워크·모델 호출 없는 입력/참조/해시/미실행 상태 검사 6개 |

fixtures는 공개 장소 데이터와 합성 시험 대화만 포함합니다. 실제 사용자 세션 ID, 인증 정보, 사용량, 과거 측정 시간을 새 평가 결과로 복사하지 않았습니다. 원본 코스의 매장명은 **부분 수정의 보존 대상**이며 새 생성의 정답 매장명은 아닙니다.

## 핵심 6종

| ID | 입력 상황 | 측정할 요청 | 필수 확인 |
| --- | --- | --- | --- |
| C01 | 광주 14시·광주역 | 자장면 → 구장 간식 → 경기 → 술집 → 산책 | 메뉴·내부 출처·13:30 내부 도착·술집 평점 |
| C02 | 잠실 17시·삼성역 서쪽 | 카페 → 구장 간식 → 경기 → 술집 → 산책 | 순서·16:30 내부 도착·술집 평점 |
| C03 | 동일 광주 원본 코스 | 경기 전 자장면 식당만 돈카츠로 수정 | 돈카츠 근거와 다른 방문 보존 |
| C04 | 동일 잠실 원본 코스 | 카페만 메가커피로 수정 | 지정 브랜드와 다른 방문 보존 |
| C05 | 동일 잠실 원본 코스 | 메가커피 + 산책 대신 호텔 숙박 | 두 변경 모두 반영, NOL 조건 근거 |
| C06 | 동일 잠실 원본 코스 | 경기 후 산책만 삭제 | 대상만 삭제, 시간표 재계산 |

경기 날짜는 **2026-10-16 시연용 가상 경기**입니다. 광주는 KIA 홈–NC 14:00, 잠실은 두산 홈–롯데 17:00입니다. 실제 공식 경기로 안내하면 실패입니다. 서버의 해당 일정 활성 여부를 실행 전에 확인해야 하며 테스트를 위해 운영 일정을 자동 변경하지 않습니다.

광주 출발점은 `35.1659, 126.9096`, 잠실은 `37.5088, 127.0611`입니다. 잠실 좌표는 기존 통합 시험에서 사용한 **시험 지점**이며 과거 사용자 핀을 정확히 복원했다고 주장하지 않습니다. 새 기본 역 시험 R06/R07은 출발 입력과 이전 기억이 모두 없는 별도 세션입니다.

C03은 비교 대상을 확정하려고 사용자의 원래 “식당이 별로다” 요청을 “경기 전 자장면 식당만”으로 구체화했습니다. 애매한 대상 선택 UI의 정확도를 이 문항의 성공으로 입증하지 않습니다.

## 채점

정답은 고정된 식당 이름 대신 방문별 종류·순서·메뉴·브랜드·출처·경기 정보로 정의합니다. `expected.visits`는 정답 **조건**이며 모델이 실제 반환한 결과가 아닙니다.

- 필수 조건 위반은 실패입니다. 코스가 빨리 나왔더라도 요청한 방문이 빠지면 전체 완료가 아닙니다.
- 근거 부족으로 판정할 수 없으면 `unverified`, 사용자의 추가 답변을 기다리면 `incomplete`, 실행 환경/제공자 오류는 `error`로 구분합니다. 분모와 사유를 함께 보고합니다.
- 정직한 미확인 안내는 근거 표현 단계에서 통과할 수 있지만 요청한 코스 생성·수정 완료로 가산하지 않습니다.
- `availability`는 확보한 근거의 적용 날짜·시간을 올바르게 판정하는 검사입니다. 영업 정보를 확보하지 못한 모든 매장을 자동 실패시키거나, 모호한 휴무 표현으로 탈락시키지 않습니다.
- 술집의 평점·평가 건수는 실제 지점 근거로 확인합니다. 구장 내부 먹거리에는 외부 평점 필터를 적용하지 않습니다.
- `BAR`는 의미상의 방문 종류입니다. 현재 공개 payload에서는 `FOOD`로 나타날 수 있으므로 실제 업종 정보와 함께 검사합니다.
- 부분 수정에서 장소 ID·이름·좌표·visitId·순서·종류·체류·고정/완료 상태를 보존합니다. 이동 변화에 따른 도착/종료 시각은 달라질 수 있습니다. R12의 카페 체류시간은 명시적 예외입니다.
- `no_extra_model`은 호출 낭비의 진단 항목입니다. 호출 횟수만으로 전체 과업을 실패 처리하거나 새로운 호출 상한을 만들지 않습니다.
- 채팅 본문에 매장명이 있다는 이유만으로 메뉴 근거·실제 지도 표시까지 통과시키지 않습니다. UI 항목은 브라우저 관측이 있어야 판정합니다.

## 실행 준비와 기록

1. 독립 검토자가 문항과 기대 조건을 검토합니다. 검토자·검토 시각과 cases/fixtures 해시를 남긴 뒤 기준을 동결합니다.
2. A/B 코드 SHA, 미커밋 파일 해시, 모델·추론 설정, 경기 자료, 제공자 설정, 백그라운드 워커와 캐시 범위를 기록합니다. 지금 확인한 최신 upstream은 cases의 code_context에 기록했고 자동 병합하지 않았습니다.
3. 생성은 독립된 게스트 시험 세션에서 시작합니다. 수정은 같은 fixture·대화·서버 기억을 A/B에 각각 복원합니다. 사용자 세션을 수정하지 않습니다. 서버 게임 출처를 복원해야 하며 클라이언트의 isDemo만 주입해서 서버 검증을 우회하지 않습니다.
4. 준비용 호출·원본 코스 생성 비용은 `setup_runs`에 별도로 남깁니다. 매번 새 코스를 만들어 다른 상호를 수정하면 공정한 짝 비교가 아닙니다.
5. 문항 순서는 고정하고 A/B 실행 순서를 번갈아 배치합니다. 핵심 6종 × 각 버전 3회 = 36개 **과업 실행** 계획입니다. 준비 호출, 추가 선택 답변, 회귀 14종은 이 숫자에 포함되지 않습니다.
6. 결과 양식을 복사하고 version_label·repeat·입력/원본 해시·실행 경계·증거 경로를 채웁니다. 원시 기록은 Git 제외 경로 `backend/artifacts/`, 검토 요약은 `docs/test_results/`에 보관합니다.
7. 실제 실행을 검토한 후에만 not_run을 바꿉니다. 결과를 보고 정답 조건을 완화하지 않습니다.

### 측정 범위

API 시간은 요청 직전부터 SSE `done` 이벤트까지입니다. 스트림 종료 시각은 별도 기록합니다. 함수 직접 실행, APIClient, 프록시를 포함한 브라우저 시간을 혼합하지 않습니다. R10/R14의 화면 완료 시간은 별도입니다.

장소 근거·숙박 원문·코스 결과 캐시와 제공자 프롬프트 캐시를 구분합니다. 운영 캐시를 삭제하지 말고, 캐시 제한 시험은 별도 격리 환경에서 범위를 명시합니다. 호출 수와 토큰 수는 JEV·채팅 모델·임베딩·검색·길찾기를 각각 기록합니다. 단가와 기준일이 확인되지 않은 금액은 null입니다.

모든 실패와 느린 표본을 남깁니다. 전체 완료율과 실패/미확인/오류 건수를 먼저 표시하고, 양쪽 모두 성공한 동일 사례 쌍의 중앙값·최대값을 별도로 비교합니다. 제외한 쌍의 수와 사유도 공개합니다. 병렬 단계 시간을 더해 전체 시간으로 쓰지 않습니다.

## 기존 도구와의 연결 범위

이 파일은 **검토 가능한 문항·기대 조건·공통 입력 규격**입니다. 실제 실행기가 연결되었다고 주장하지 않습니다.

- `evaluate_courses`의 `Capture`, `current`, 기존 저장/원본 비교 검사는 후속 계측 연결에 재사용할 수 있습니다. 현재 명령의 scenarios는 코드에 고정되어 있으며 `--dataset` 인자는 없습니다.
- `chat_eval --questions`는 별도 JSONL 형식으로 그래프를 직접 실행합니다. 지도 context/currentCourse와 SSE 저장 경계를 그대로 재현하지 못하므로 이 파일을 변환해 돌린 결과를 전체 코스 평가로 취급하지 않습니다.
- 현재 DeepEval/Ragas golden·judge에 자동 등록하거나 실제 모델 호출을 추가하지 않습니다. 단계별 의미 평가를 할 때는 해당 프레임워크에 맞는 독립 정답/실제 출력/근거를 연결해야 합니다.
- 수동 평가도 같은 문항·fixture·원시 증거·기록 양식으로 수행할 수 있습니다. 자동 실행까지 필요하면 기존 evaluate_courses의 입력과 검사 연결을 좁게 추가하는 후속 작업이 필요합니다.

## 데이터 무결성 검증

다음 명령은 JSON·참조·시간 조건·fixture 해시·빈 측정값만 검사하며 모델/네트워크/DB를 호출하지 않습니다.

```powershell
python -I .github/evaluation_ci.py offline-exec backend/llm/v2/evaluation/test_course_dataset.py -v
```

2026-10-13 실행 결과는 **무결성 검사 6개 통과**입니다. 이는 20개 코스 요청의 성공률이 아닙니다.

CI 연결은 `.github/workflows/evaluation-regression.yml`의 `deterministic` job → `.github/evaluation_ci.py free` → `test_course_dataset.py -v`입니다. 동일 offline-exec 경로의 해당 테스트 명령을 로컬에서 실행했습니다. GitHub 원격 CI 전체·실제 제공자 A/B는 이번 작업에서 실행하지 않았습니다.

기존 CI 연결 검사도 확인했습니다. 전체 10개 첫 실행에서는 로컬 Python의 Django·LangSmith 부재로 2개, Windows 기본 인코딩 때문에 1개가 오류였습니다. UTF-8 모드에서 의존성이 없는 8개를 재실행해 모두 통과했고, 새 검사 등록으로 무료 명령 수가 8개에서 9개가 된 기대값도 갱신했습니다. Django export/기존 DeepEval 입력 연결 2개는 평가 의존성을 갖춘 격리 환경에서 재검증해야 합니다. 이를 전체 CI 통과로 표시하지 않습니다.
